## 1. Contract authority

This contract defines the logical interface and outcomes for Factory Portal provisioning and DCAM device identity restoration. Spring Boot BFF is the exclusive API, authorization and audit boundary. PostgreSQL ddmp is authoritative.

Factory Portal requests are administrative. Device restoration requests are device-facing. They use distinct credentials/scopes and must never be interchangeable.

## 2. Identity vocabulary

Term

Meaning

serial_number

Hardware/recovery key. It originates from a DCAM-generated QR and is read-only in Factory Portal.

dcam_cloud_device_id

Canonical cloud device identity created/restored by BFF.

platformDeviceId

BFF↔DCAM contract name for the same logical identity as dcam_cloud_device_id.

correlationId

Request/audit identifier supplied or generated by BFF.

publicKeyFingerprint

Non-secret fingerprint of the Android Keystore public key in DCAM QR; BFF binds it to a short-lived pending enrollment.

pairingNonce

Fresh non-secret QR pairing nonce/correlation value; validated for freshness/replay policy.

pendingEnrollment

BFF state that authorizes a later Device API proof-of-possession attempt. It is not a device credential or certificate.

## 3. Administrative provisioning action

```
POST /admin/v1/factory/provisioning/devices
```

Preconditions:

authenticated Factory Worker subject;

server-side role/workspace authorization;

valid QR-derived serial input;

approved CSRF/session protection.

Logical request:

{
  "qrPayload": "raw DCAM QR non-secret pairing payload, or approved server-side scan reference",
  "workspaceId": "authorized factory workspace",
  "requestId": "idempotency/correlation value"
}
Logical success/known outcomes:

{
  "outcome": "CREATED | RESTORED | CONFLICT | REJECTED",
  "platformDeviceId": "canonical dcam_cloud_device_id when allowed",
  "enrollmentState": "PENDING_ENROLLMENT | NOT_CREATED",
  "correlationId": "stable audit reference",
  "reasonCode": "stable non-sensitive code"
}
The server validates QR signature/freshness and extracts serial_number, publicKeyFingerprint and pairingNonce server-side. It selects create versus restore, creates a short-lived PENDING_ENROLLMENT when allowed and writes audit. A duplicate serial must not create a second logical device identity. The response never contains a device certificate, challenge secret or private-key material.

## 4. Device-facing enrollment and identity restore

DCAM uses a distinct BFF device-facing flow defined by the Device Integration Contract. Against the pending enrollment, it proves possession of the Android Keystore private key by completing a BFF challenge; BFF then binds/issues the client certificate according to Device PKI design and returns the canonical identity/certificate chain or safe retry/rejection result. It does not receive Factory Worker session data and it cannot invoke administrative routes.

## 5. BFF-owned logical data areas

Area

Purpose

Factory worker authorization

Subject-to-factory-role/workspace mapping, owned by BFF.

Device identity registry

Unique serial-to-dcam_cloud_device_id mapping and lifecycle state.

Provisioning request/idempotency

Replay-safe create/restore request record.

Pending enrollment

Short-lived serial/public-key-fingerprint/pairing-nonce/correlation binding, expiry and result state; no private key or worker credential.

Provisioning audit

Append-oriented action/result history with actor and correlation context.

Exact table names, columns, indexes, retention and migration mechanics are implementation details. No browser uses direct SQL or a data-store SDK.

## 6. Security and compatibility rules

IdP provider/protocol and exact tokens/cookies are deliberately not fixed here; they require security review. No Firebase/BaaS or hosted data provider is introduced. An approved external or self-hosted IdP is a BFF-integrated security dependency only.

BFF authenticates and authorizes every administrative request. UI visibility is not sufficient.

No request/response/QR/audit event may expose Wi-Fi password, private key, certificate private material, secrets or long-lived device credential.

Existing legacy provider data, if any, must be migrated through a BFF-controlled migration with reconciliation and audit; no dual write or parallel data authority is permitted.

Management configuration/update remains the DDMP BFF desired-state contract; this factory contract does not grant Headwind authority over device identity.

## 7. Deferred detail

QR cryptographic format, nonce/freshness values, exact endpoint versioning, Device PKI certificate profile/challenge details, schema DDL, response field names beyond this logical model, retention and environment topology remain gated design decisions.

## 8. Approved runtime placement

Factory Portal is rendered by Spring MVC/Thymeleaf inside the ddmp-bff Docker container on Server A. It is not a separate Portal deployment and is never deployed into the headwind-tomcat container. PostgreSQL ddmp is host-native on Server B; browser clients have no database route. The deployment contract is owned by DDMP BFF Bootstrap and DDMP 10.
